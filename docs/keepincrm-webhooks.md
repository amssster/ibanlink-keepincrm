# IBAN Link: налаштування вихідних Webhooks KeepinCRM

Покрокова інструкція з підключення вихідних тригерів KeepinCRM до **IBAN Link** — сервісу платіжних посилань на IBAN — через механізм **Response**.

---

## 1. Підготовка в KeepinCRM

Для роботи потрібен розширений тариф KeepinCRM з підтримкою тригерів.

### Додаткові поля в Угодах (Налаштування → Угоди → Додаткові поля):
1. **Поле для посилання:** назва `Посилання на оплату IBAN` (або власна, вказується в налаштуваннях сервісу), тип — **Текст** або **Посилання**.
2. **Поле вибору отримувача:** назва `Отримувач платежу`, тип — **Список (select)**.
   - Варіанти списку мають **посимвольно збігатися** з ключами отримувачів у кабінеті сервісу (розділ «Отримувачі»). Наприклад: `Основний`, `ФОП 1`, `ТОВ Вектор`.
   - Регістр, пробіли та розділові знаки мають бути ідентичними (точний збіг). Будь-яка описка (наприклад, помилка в одну літеру або зайвий пробіл) призведе до блокування видачі посилання (`no_recipient`).
   - **Порада:** завжди копіюйте ключ кнопкою копіювання безпосередньо зі сторінки «Отримувачі» в кабінеті IBAN Link, а не вводьте вручну.

---

## 2. Тригер створення посилання (issue)

Спрацьовує при переході угоди на етап оплати. Повертає готове платіжне посилання через Response та записує його в угоду без викликів API.

- **Розділ:** Налаштування → Тригери → Додати тригер
- **Таблиця з даними:** `Угоди`
- **Дія:** `Webhook`
- **URL:** `https://ваш-домен/api/webhooks/keepincrm/issue`
- **Метод відправки даних:** `POST`
- **Успішний статус запиту:** `200`
- **Content-Type:** `application/json`
- **Заголовки:**
  ```http
  Authorization: Bearer <WEBHOOK_ISSUE_SECRET>
  ```
  *(значення **`WEBHOOK_ISSUE_SECRET`** із вашого `.env` або змінних оточення)*

> **Зверніть увагу на заголовок Authorization:**
> - **Два різні секрети:** тригер угод (`/issue`) перевіряє **`WEBHOOK_ISSUE_SECRET`**, а тригер фінансів (`/payment`) — **`WEBHOOK_PAYMENT_SECRET`**. Не використовуйте секрет платежів у тригері угод, інакше сервер поверне помилку 401 (`{"error":"Недозволений запит"}`).
> - **Вузьке поле вводу в KeepinCRM:** поле «Значення» в інтерфейсі KeepinCRM коротше за 71 символ (`Bearer ` + 64-значний ключ). Після вставки видима лише частина рядка, а решта прокручується горизонтально — це нормальна поведінка, ключ не обрізається. Переконайтеся, що на початку є `Bearer ` з одним пробілом, а в кінці немає зайвих пробілів або переносів.
> - **Оновлення секретів у Coolify/Docker:** якщо ви змінили або додали змінну оточення в панелі керування (наприклад, Coolify), новий секрет потрапить у додаток **тільки після перезапуску (Redeploy)**. До редеплою сервер продовжуватиме очікувати старе значення.

- **Умова виконання:**
  ```text
  stage.name == 'Очікує оплати'
  ```
  *(вкажіть назву вашого етапу оплати в одинарних лапках. Тільки код, без описового тексту!)*
- **Метод запуску:** `Відразу`

### Тіло запиту (Body JSON):
```json
{
  "event_id": "issue:{{id}}:{{updated_at}}",
  "deal_id": "{{id}}",
  "event_at": "{{updated_at}}",
  "total": "{{total}}",
  "paid": "{{paid}}",
  "currency": "UAH",
  "stage": "{{stage.name}}",
  "recipient_key": "{{custom_fields.ваша_системна_назва_поля}}"
}
```

> **Важливо:**
> - `event_id` **обов'язково** повинен містити `{{updated_at}}` (наприклад, `"issue:{{id}}:{{updated_at}}"`). Якщо передати тільки ID угоди, кожна наступна зміна повертатиме HTTP 409 (конфлікт стабільного ID події).
> - `currency` вказується літералом `"UAH"`.
> - **`recipient_key` і префікс `custom_fields.`:** у KeepinCRM усі користувацькі поля в тілі запиту обов'язково повинні починатися з префікса `custom_fields.`. Замініть `ваша_системна_назва_поля` на системну назву вашого поля «Отримувач платежу» зі списку доступних змінних редактора тригера. Наприклад, якщо в списку змінних поле має вигляд `otrimuvach_platiezhu_665`, у JSON має бути `"{{custom_fields.otrimuvach_platiezhu_665}}"`, а **не** `"{{otrimuvach_platiezhu_665}}"`.
> - Якщо поле «Отримувач платежу» не заповнене або в ньому невідомий ключ — посилання не створиться, подія буде пропущена (`no_recipient`), поле в CRM залишиться порожнім. Це захист від оплати не на того отримувача.

### Успішна відповідь (Response):
1. У блоці «Успішна відповідь (Response)» натисніть **«Додати»**.
2. Оберіть поле угоди: `Посилання на оплату IBAN`.
3. Вкажіть JSON-шлях: `$.payment_url`.

## 3. Тригер підтвердження оплати (payment)

Спрацьовує при створенні фактичного вхідного платежу у вкладці «Фінанси».

- **Таблиця з даними:** `Фінанси`
- **Дія:** `Webhook`
- **URL:** `https://ваш-домен/api/webhooks/keepincrm/payment`
- **Метод відправки даних:** `POST`
- **Успішний статус запиту:** `200`
- **Content-Type:** `application/json`
- **Заголовки:**
  ```http
  Authorization: Bearer <WEBHOOK_PAYMENT_SECRET>
  ```
  *(окремий секрет для платежів)*

- **Умова виконання:**
  ```text
  created_at
  ```
  *(або з фільтрацією доходів по угодах: `created_at and kind == 'debit' and parent_id != NULL`). Вказуйте тільки системний код без лапок і без слів «Створення запису»!*
- **Метод запуску:** `Відразу`

### Тіло запиту (Body JSON):
```json
{
  "event_id": "payment:{{id}}",
  "payment_id": "{{id}}",
  "deal_id": "{{parent.id}}",
  "event_at": "{{created_at}}",
  "total": "{{parent.total}}",
  "paid": "{{parent.paid}}",
  "currency": "{{currency}}",
  "kind": "{{kind}}",
  "planned": "{{planned}}"
}
```

> **Важливо:**
> - **Умова виконання:** у полі вказуйте системний код `created_at` (або `created_at and kind == 'debit' and parent_id != NULL`). Не пишіть описовий текст на зразок «Створення запису» — це викличе помилку `Condition expression Invalid statement`.
> - Блок «Успішна відповідь (Response)» у платіжному тригері залишайте **порожнім**.
> - `paid` — це накопичувальна сума оплат за угодою після проведення платежу (`{{parent.paid}}`), а не сума одного чека.
> - `{{currency}}` залишається змінною навмисно: якщо надійде платіж у валюті, відмінній від UAH, запит завершиться 400 і буде зафіксований у журналі.
> - **Обмеження create-only:** тригер спрацьовує на подію створення платежу. Якщо платіж створено «Запланованим» (`planned: true`), посилання не закриється. Коли статус пізніше змінюється на «Проведений», тригер створення повторно не надсилається. Тому створюйте фактичні платежі одразу проведеними (або скасовуйте посилання вручну в кабінеті).

## 4. Чеклист активації

Перед тим, як увімкнути інтеграцію:

1. **Збережіть реквізити та мапінг** у кабінеті з вимкненим прапорцем активації.
2. Створіть **одну конкретну тестову угоду** в KeepinCRM:
   - Оберіть у ній поле «Отримувач платежу» зі списку.
   - **Важливо:** значення має **посимвольно збігатися** з «Ключем отримувача» в кабінеті (`/admin/recipients`), включно з регістром, пробілами та крапками (наприклад, `Основний` або `ТОВ Вектор`). Будь-яка описка викличе помилку невідповідності ключа.
3. Переведіть цю угоду на етап оплати (спрацює тригер `issue`):
   - У кабінеті в розділі «Події» з’явиться подія `Запит на посилання` зі статусом `Перевірка контракту`.
   - В угоду в CRM запишеться тестовий URL виду `https://ваш-домен/integration-check`.
4. Створіть проведений платіж у вкладці «Фінанси» **в цій же самій тестовій угоді** (спрацює тригер `payment`):
   - У розділі «Події» з’явиться подія `Проведення платежу` зі статусом `Перевірка контракту`.
   - Обидві події (`issue` та `payment`) обов'язково повинні належати **одному ID угоди**, інакше система відхилить активацію (`Потрібні події однієї тестової угоди`).
   - Перевірте, що платіж проведений (`planned: false`), вхідний (`kind: debit`) та у валюті `UAH`.
5. Поверніться на сторінку «Підключення» (`/admin/settings`):
   - У кроці 04 («Активація») обов'язково позначте **обидва чекбокси одночасно**:
     - `[x]` «Я перевірив суми, валюту, час, обидві події та запис тестового посилання в угоду через Response.»
     - `[x]` «Увімкнути інтеграцію»
   - Натисніть **«Зберегти налаштування»**.
   - *Зверніть увагу:* чекбокс «Я перевірив...» не зберігається в базі даних як окреме налаштування, це разовий запобіжник. Якщо позначити тільки його без «Увімкнути інтеграцію» — сервіс не активується, а після оновлення сторінки прапорець знову буде порожнім.

## 5. Troubleshooting (типові помилки)

| Проблема / Помилка | Причина | Що робити |
|---|---|---|
| `Потрібні тестові події створення посилання та проведеної оплати` | Немає обох тестових подій (`issue` та `payment`) у статусі перевірки контракту після останньої зміни налаштувань | Перевірте налаштування обох тригерів. Переведіть тестову угоду на етап оплати, а потім створіть у ній проведений платіж у Фінансах. |
| `Тестова подія створення посилання повинна містити ключ отримувача з налаштувань` | Ключ отримувача з CRM не збігається з ключем у кабінеті (`/admin/recipients`), або в ньому є описка | Порівняйте значення в CRM і в кабінеті посимвольно (наприклад, описки в літерах `в` замість `к`, зайві пробіли чи крапки). Збережіть виправленого отримувача в кабінеті, перевиберіть його в тестовій угоді та надішліть свіжі події. |
| `Потрібні події однієї тестової угоди` | Останній `issue` та останній `payment` надійшли з різних угод CRM | Проведіть повний тест на **одній угоді**: спочатку переведіть її на етап оплати, потім додайте платіж саме в цю угоду. |
| `Підтвердьте перевірку сум, часу, подій та запису тестового посилання через Response` | Увімкнено чекбокс «Увімкнути інтеграцію», але не позначено чекбокс підтвердження перевірки | Позначте обидва чекбокси одночасно перед натисканням «Зберегти налаштування». |
| Галочка «Я перевірив...» скидається після перезавантаження екрана | Перший чекбокс є разовим підтвердженням і не зберігається окремо без увімкнення інтеграції | Позначте **обидва чекбокси одночасно** («Я перевірив...» + «Увімкнути інтеграцію») і натисніть «Зберегти налаштування». |
| Після зміни отримувача активація знову вимагає перевірку | Будь-яка зміна платіжних реквізитів або списку отримувачів скидає контрактний таймлайн (`contractSince`) | Після редагування реквізитів знову проведіть тестову угоду (переведення на етап + платіж) та активуйте інтеграцію. |
| `Condition expression Invalid statement` | У полі «Умова виконання» введено людський текст замість коду | Вкажіть системний вираз KeepinCRM: `created_at` для фінансів або `stage.name == '...'` для угод. |
| HTTP 409 у тригері issue | `event_id` не містить timestamp або відсутній залишок | Додайте `{{updated_at}}` до `event_id` (`issue:{{id}}:{{updated_at}}`). Перевірте `total - paid > 0`. |
| Посилання не з'явилося, в подіях `no_recipient` | 1) У тілі тригера не вказано обов'язковий префікс `custom_fields.` (вказано `"{{поле}}"` замість `"{{custom_fields.поле}}"`).<br>2) Поле «Отримувач платежу» в угоді не заповнене.<br>3) Описка у вибраному варіанті в CRM (не збігається з ключем у кабінеті посимвольно, наприклад зайвий пробіл, крапка або інша літера). | 1) Перевірте тіло тригера: `"recipient_key": "{{custom_fields.ваша_назва_поля}}"`.<br>2) Скопіюйте ключ отримувача кнопкою копіювання з кабінету та вставте у варіанти випадаючого списку KeepinCRM.<br>3) Перевиберіть отримувача в угоді та збережіть її. |
| В подіях `recipient_suspended` | Отримувача тимчасово призупинено в кабінеті | Відновіть отримувача в кабінеті (розділ «Отримувачі»). |
| HTTP 400 у тригері payment | `kind` не `debit`, або валюта не `UAH`, або платіж запланований | Перевірте, чи платіж вхідний, проведений та у гривні. |
| Після зміни реквізитів посилання не створюються | Зміна платіжних реквізитів скидає активацію | Зробіть тестовий пробіг і активуйте сервіс повторно в кабінеті. |
| HTTP 401: `{"error":"Недозволений запит"}` | 1) **Переплутано секрети:** для тригера угод (`/issue`) вказано `WEBHOOK_PAYMENT_SECRET` замість `WEBHOOK_ISSUE_SECRET`.<br>2) **Не виконано Redeploy:** змінну оновлено в Coolify/Docker, але контейнер не перезапущено.<br>3) **Формат заголовка:** відсутнє слово `Bearer ` перед токеном або є зайві пробіли. | 1) Для тригера угод вкажіть `Bearer <WEBHOOK_ISSUE_SECRET>`, для фінансів — `Bearer <WEBHOOK_PAYMENT_SECRET>`.<br>2) У Coolify після зміни змінних обов'язково натисніть **Redeploy**.<br>3) Перевірте формат: рівно один пробіл між `Bearer` і 64-значним hex-рядком. |
| Помилка `Origin` у браузері кабінету | Зовнішня адреса відрізняється від `APP_URL` | Доступ до кабінету дозволено лише за адресою, вказаною в `APP_URL`. |
| Помилка Telegram-сповіщення | Помилка відправлення або відсутні надійні дані платежу | Перевірте причину в розділі «Події». Допустиму операцію можна повторити вручну; автоматичного повтору немає. |
| Операція `skipped` | Операцію пропущено, зокрема через відсутні налаштування Telegram | Перевірте налаштування та причину пропуску; `skipped` не означає успішне надсилання. |

Якщо результат відправлення невідомий, зокрема після тайм-ауту, перевірте Telegram перед ручним повтором: повідомлення могло надійти, а повтор може створити дубль. Одноразове надсилання не гарантується.

Історія вхідних подій автоматично не видаляється. Власник має стежити за зростанням бази даних і доступним місцем та забезпечувати резервне копіювання.
