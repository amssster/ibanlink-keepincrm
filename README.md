# IBAN Link · для KeepinCRM

> **IBAN Link — self-hosted payment link service for Ukrainian businesses using KeepinCRM.**
> Automatically creates branded payment pages with official NBU QR codes and direct Monobank / Privat24 app integration based on KeepinCRM deal stages. Fully self-hosted, single-tenant, with zero platform transaction fees.

Публічний сайт та підтримка: [ibanlink.online](https://ibanlink.online).

**IBAN Link для KeepinCRM** — власний автономний сервіс випуску платіжних посилань для розрахункового рахунку IBAN.
Менеджер у KeepinCRM обирає отримувача платежу (ФОП/ТОВ) та переводить угоду на етап очікування оплати. 
Сервіс миттєво генерує унікальну сторінку оплати за стандартом НБУ з QR-кодом і кнопками відкриття банків (Monobank, Приват24) та повертає посилання прямо в угоду через механізм **Response** (без доступу до API CRM).

Коли бухгалтер або менеджер проводить платіж у вкладці «Фінанси», платіжна сторінка автоматично закривається, а власник може отримувати сповіщення в Telegram.

---

## Основні можливості

- **Кілька отримувачів (Мультотримувачі):** підтримка кількох рахунків (ФОП 1, ФОП 2, ТОВ). Вибір рахунку через select-поле «Отримувач платежу» в KeepinCRM.
- **Індивідуальні реквізити та призначення:** кожен отримувач має власні юридичні реквізити (IBAN, ЄДРПОУ/РНОКПП), бренд, логотип, нотатку покупцю та власний шаблон призначення платежу.
- **Стандарт НБУ 002:** повна сумісність із правилами Національного банку України (постанова №97). QR-код сканується будь-яким банківським додатком.
- **Миттєвий перехід до банку:** кнопки для швидкого відкриття Monobank та Приват24 на смартфонах Android та iOS.
- **Завантаження QR-коду:** клієнт або менеджер може завантажити QR-код у форматі PNG одним кліком.
- **Керування терміном дії:** гнучке налаштування TTL посилань (1–30 днів, за замовчуванням 7 днів) та кнопка «Продовжити» в кабінеті.
- **Призупинення отримувачів:** тимчасове вимкнення прийому платежів на конкретний рахунок без видалення та скидання налаштувань.
- **Сповіщення в Telegram:** миттєві повідомлення власнику про успішно проведені повні або часткові оплати через Telegram Bot API.
- **Зручний кабінет власника:** пошук за номером угоди та подіями, фільтри за датами і статусами, повноцінна пагінація, журнал вхідних подій та черги.
- **Працює без API-ключа CRM:** використовує лише вихідні Webhooks з Response-мапінгом — без ризику витоку бази клієнтів.

## Схема взаємодії

```
KeepinCRM (Угода) ───[Webhook POST: issue]───► Сервіс IBAN Link
KeepinCRM (Угода) ◄──[Response: payment_url]── Сервіс IBAN Link
       │
  (URL передається клієнту)
       ▼
Клієнт відкриває сторінку /p/{token} ──► Оплата в банку (QR / Mono / Приват24)
       │
  (Менеджер звіряє виписку)
       ▼
KeepinCRM (Фінанси) ──[Webhook POST: payment]─► Сервіс IBAN Link (Закриває лінк + сповіщення)
```

## Налаштування KeepinCRM

Детальна покрокова інструкція з копіюванням JSON-шаблонів та налаштуванням тригерів описана в документі:
👉 **[Інструкція з налаштування KeepinCRM Webhooks](docs/keepincrm-webhooks.md)**

Короткий алгоритм:
1. У кабінеті сервісу (розділ «Отримувачі») додайте отримувачів (ФОП, ТОВ) з реквізитами та призначеннями платежів.
2. В угодах KeepinCRM створіть поле `Посилання на оплату IBAN` (текст/посилання) та список `Отримувач платежу` зі значеннями, які точно збігаються з ключами отримувачів.
3. Додайте два вихідних Webhooks (створення посилання з відповіддю через `$.payment_url` та фіксація оплати у Фінансах).
4. Проведіть одну тестову угоду (переведення на етап оплати + створення проведеного платежу в цій же угоді), у кроці «Активація» позначте обидва чекбокси одночасно та збережіть налаштування.

## Резервне копіювання (Docker)

Контейнер `backup` створює дамп при старті та приблизно кожні 24 години. Скрипт видаляє файли `iban-*.dump` старші за 14 днів під час успішного створення копії. У `compose.yaml` копії зберігаються в `backups/` на хості, у `compose.coolify.yaml` — у томі `backups`. Дампи не шифруються та можуть містити персональні дані й токен Telegram. Обмежте доступ, зберігайте зашифровані копії окремо від сервера та перевіряйте їх відновлення.

Створити разовий бекап вручну:
```sh
docker compose exec backup sh /ops/backup.sh
```

Безпечна перевірка відновлення без зупинки робочої бази:
```sh
docker compose exec backup sh /ops/restore-check.sh /backups/iban-YYYYMMDDTHHMMSSZ.dump
```

Підставте назву наявного дампа. Перевірка створює тимчасову базу на тому самому сервері PostgreSQL, відновлює дамп, перевіряє кількість записів у трьох таблицях і видаляє тимчасову базу; потрібні право створення баз та вільне місце. Це не перевірка всіх даних і не відновлення робочої бази. Для Coolify використовуйте відповідний файл Compose або термінал сервісу `backup`.

Для реального відновлення спочатку збережіть актуальний стан, зупиніть записи застосунку та відновіть копію в окрему порожню базу. Перевірте дані й міграції, лише потім переключіть застосунок; не відновлюйте дамп поверх робочої бази. Доступ до дампів і відновленої бази має бути обмежений.

## Події та сповіщення

У розділі «Події» власник може вручну повторити невдалу або очікувану операцію, а також операцію, що надто довго перебуває в обробці. Невдалі Telegram-сповіщення автоматично не повторюються. Стан `skipped` означає, що операцію пропущено; зокрема, сповіщення не надсилається, якщо Telegram не налаштовано.

Якщо результат відправлення невідомий, наприклад через тайм-аут, перед повтором перевірте Telegram: повідомлення могло надійти, і повтор може створити дубль. Гарантії одноразового надсилання немає.

Історія вхідних подій автоматично не видаляється. Власник відповідає за моніторинг зростання бази даних, доступного місця та резервне копіювання.

## Обмеження сервісу

- Валюта: тільки **UAH** (гривня).
- Модель: один бізнес на один екземпляр (self-hosted single tenant, без мультиакаунтів).
- Автопідтвердження надходжень через банківські виписки або динамічні коди в призначення платежу не виконується — зарахування платежів перевіряє менеджер/бухгалтер за банківською випискою.
- Замовлення з порожнім полем «Отримувач платежу» пропускаються без генерації посилання для запобігання переказам на помилковий рахунок.
